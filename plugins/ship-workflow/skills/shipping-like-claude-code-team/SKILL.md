# Shipping like the Claude Code team

## Overview

This is the working loop behind the public anthropics/claude-code repository. It is reconstructed from PRs, commit trailers, review threads, slash commands, workflows and mod sources (see `references/sources.md`).

**Core principle:** the engineer owns each decision. Claude does the work and proves it. A different human approves. A rule that matters is enforced by code, not by a prompt alone.

## When to use

- Any feature, bug fix or refactor that ends in a PR.
- Writing commit messages, PR descriptions, or replies to review comments.
- Reviewing a diff or PR with several agents.
- Putting Claude in CI: `@claude`, issue triage, dedupe, scheduled agents.

Do not use for one-line typo fixes or throwaway scripts. For those, edit, verify, and stop.

## The loop

| # | Phase | Who | Output | Gate before next phase |
|---|---|---|---|---|
| 1 | Ask | Engineer | Request in a session, cloud session or project thread | None |
| 2 | Explore | Claude + parallel explorer agents | Map of the code; Claude reads the 5–10 key files | None |
| 3 | Clarify | Claude | One batched list of questions | **Answers received** |
| 4 | Design | Claude (+ 2–3 architect agents for big work) | Options with trade-offs and one recommendation | **Engineer picks one** |
| 5 | Build | Claude | Tests first, then small commits, one reason each | Tests pass |
| 6 | Self-verify | Claude | The repo's own checks run, edge cases run, a "not tested" list | Every check passes |
| 7 | Review | Reviewer agents by angle, then one validator per finding | Only validated findings | Findings fixed or put to the engineer |
| 8 | PR | Claude | A body that follows the PR contract below | None |
| 9 | Review replies | Claude, checked by the engineer | A reply backed by evidence; scope kept | None |
| 10 | Merge | **A different human** | Approval; first real runs watched | None |

Phase details, model choices and entry points are in `references/feature-lifecycle.md`.

## Hard gates

1. **Do not implement a non-trivial change before the engineer approves the design.** A small change counts as trivial only when it has one obvious design and touches no auth, security, data or public API.
2. **Do not report a result that has not happened.** CI, deploys and real runs that come after the merge go under "Not tested yet".
3. **Do not widen a PR to fix a problem that predates it.** Record it under Risk or Follow-up, and tell the engineer.
4. **Do not merge your own work.** Leave that to a human who did not write it.

| Rationalization | Reality |
|---|---|
| "They said ship today, so defaults are fine" | Urgency is not approval. Ask one batched question with a recommended default, then wait. |
| "CI will pass, so I'll write green" | Write "Not run on CI yet". Fill it in after it runs. |
| "It's a quick fix, so I'll add it to this PR" | Mixed scope hides risk from the reviewer. Open a follow-up instead. |
| "The reviewer is probably right" | Verify against the code and real data, then reply with the numbers. |
| "One reviewer pass is enough" | Run reviewers from different angles, then validate each finding separately. False positives erode trust. |

## PR body contract

Each slot is REQUIRED. Write "None" if a slot is empty.

```
## Summary        what changed; a before→after table if there are several targets
## What changes for users   behaviour per version or surface, migrations, breakage
## Testing        what ran, where, on which versions — then "Not tested:" with a list
## Risk           real-world effects if this is wrong, and what will be watched after merge
## After merge / Follow-up   manual steps left for humans; issues found but not fixed
Merge order: …   (only if another PR must land first)
_Generated by Claude Code_ (+ session link if one exists)
```

## Commit contract

The subject is an imperative verb phrase that states the effect. The body says **why**, and names the constraint or issue that forced the change. If an outside fact drives the change, cite it (`see owner/repo#1853`). Add a merge precondition if one exists. Make one commit per logical step. If you fix your own mistake, say so plainly ("Remove a compiled Python file committed by mistake"). Use the co-author trailer, and add `Claude-Session: <url>` when a session link exists.

## Review reply contract

1. Restate the claim.
2. Check it in the code.
3. Measure it on real data, as a sample with counts.
4. Give the verdict: true or false, and whether this PR caused it.
5. State the action: fixed here, or out of scope and recorded under Risk or Follow-up and flagged to its owner.

## Agents in CI

Prompt rules alone failed the baseline test. Every layer in `references/ci-agents.md` is REQUIRED:
- An egress allowlist.
- Short-lived auth.
- Auto permission mode.
- Disallowed write and web tools.
- Wrapper scripts that bind the target from the event payload.
- Per-script call caps.
- Validated output.
- A deterministic script, with a human veto window, takes irreversible actions.
- A CI check enforces all of the above.

## Red flags. Stop and fix.

- Writing code while a clarifying question is still open.
- A PR body without a "Not tested" line.
- The word "green", "passes" or "verified" about something you did not run.
- A model-chosen issue or PR number passed to a write command.
- `gh issue comment` or `gh issue edit` allowed raw to an agent.
- A rule written only in CLAUDE.md, with no check behind it.
