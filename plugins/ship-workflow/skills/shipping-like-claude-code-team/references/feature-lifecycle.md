# Feature lifecycle, step by step

## Entry points (how work starts)

| Entry | Trace it leaves | When to use |
|---|---|---|
| Local session in terminal or IDE | Commit trailer `Claude-Session: https://claude.ai/code/session_…`, PR footer "Generated by Claude Code" | Work that needs local tools, secrets or a fast loop |
| Cloud session | Branch `claude/<topic>-<random>` | Self-contained changes. The engineer reviews the branch later. |
| Project thread (team chat channel) | PR body starts `Human: @login` and "Requested by <name> · project thread" | Small asks from a conversation. Claude opens the PR itself. |

Whatever the entry, Claude makes the commits (author `Claude <noreply@anthropic.com>`) and the engineer is the co-author, or the reverse. Every artifact links back to its session.

## Phase 1: Ask

The engineer states the goal in one or two sentences. The goal states the effect, not the steps. Example: "Move the workflows that call Claude to Sonnet 5.5."

## Phase 2: Explore

- Small change: Claude reads the relevant files directly.
- Larger change: launch 2–3 explorer agents in parallel on a cheap or mid model, each with a different angle:
  - similar existing features, traced end to end;
  - the architecture and abstractions of the area;
  - extension points, UI patterns and test approach.
- Each explorer returns a **list of 5–10 key files** plus findings. Claude then reads those files itself. Never act only on a summary.
- Also find the hidden constraints that change the plan. Examples from real PRs: the new model lacks the todo tools, so the prompt must drop "make a todo list"; auto mode does not run on models older than X; a client below version N does not read the `renames` map.

## Phase 3: Clarify. Gate.

- List what the request leaves open: edge cases, error handling, scope boundaries, backward compatibility, performance, versions to support.
- Ask them all in **one batch**. Give each question a recommended default.
- **Wait.** If the engineer says "whatever you think", state the recommendation and get an explicit yes.

## Phase 4: Design. Gate.

- Big work: run 2–3 architect agents in parallel, one per stance: **minimal** (least change, most reuse), **clean** (best abstractions), **pragmatic** (balanced).
- Small work: Claude writes the options itself.
- Present a short summary of each option, the trade-offs, the concrete code differences, and **one recommendation with its reason**.
- **Wait for the pick.** Do not start building without approval.

## Phase 5: Build

- Write a failing test first, if the repo has tests.
- Make one commit per logical step. Each commit message carries its own why (see SKILL.md, commit contract).
- Follow the repo's conventions and CLAUDE.md strictly.
- Keep scope tight. In the PR body, list what you deliberately left unchanged ("Triggers, conditions, permissions, prompts, allowed tools and action references are unchanged.").

## Phase 6: Self-verify

- Run the repo's own checks: tests, typecheck, lint, and **any check that enforces a CLAUDE.md rule** (for example `check_workflow_hardening.py passes`).
- Test the edge cases explicitly. Real example: "skips a PR from a fork **and one from a deleted fork**, goes on with one from the same repository."
- Test against several versions or environments where users vary ("On 2.1.144, 2.1.193 and 2.1.310 … installed, updated across it, installed all 12 fresh").
- Stub side effects you cannot safely trigger ("with writes stubbed").
- For an agent workflow, test the CI agent end to end by posting exact `@claude` prompts (see `prompt-patterns.md`).
- Write the **not-tested list** now, while you know it: "Not run on GitHub", "Windows, restricted networks", "`@claude` mentions were not tested".

## Phase 7: Review

See `multi-agent-pipelines.md`. The short form:
1. Reviewers run in parallel from different angles.
2. One validator runs per finding.
3. Unvalidated findings are dropped.
4. The rest go to the engineer, who chooses: fix now, fix later, or accept.

## Phase 8: PR

Fill the PR body contract from SKILL.md. Each slot is required. Add a "Merge order" line if another PR must land first.

## Phase 9: Review replies

Follow the review reply contract from SKILL.md. Real example of the right shape:

> "I checked this against the code and the data, and you're right. These labels are applied with `GITHUB_TOKEN`, so their `labeled` events don't start `issue-lifecycle-comment.yml`. In a sample of 26 issues … none has the warning comment, and 20 have the closing comment. This predates this PR and doesn't depend on the model, so I'm not fixing it here. I've added it to the risks in the description and flagged it to the PR's author."

## Phase 10: Merge and watch

- A different human approves. Approval often comes within minutes for small, well-described PRs (one 3-line PR merged 23 minutes after it opened).
- After merge, watch the first real runs. Say in the PR that you will ("We'll check the first runs after merge").
- If a real run exposes a gap, open a new small PR. Do not reopen the scope of the old one.

## Model tiering

| Job | Model tier |
|---|---|
| Gate checks (is it closed, a draft, trivial, already done?), finding file paths | Smallest (Haiku) |
| Summaries, rule-compliance checks, triage, dedupe search | Mid (Sonnet) |
| Bug hunting, validating bug findings, architecture | Top (Opus) |

Pin exact model IDs in automation. When a model changes, re-read every prompt the model runs: tool availability and behaviour differ.
